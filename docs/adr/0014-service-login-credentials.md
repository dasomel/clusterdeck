# ADR-0014: Reveal service login credentials for discovered endpoints

Status: Proposed

## Context

ClusterDeck discovers ingress/gateway endpoints (`k8s_endpoints.rs`, `DiscoveredEndpoint { host, ip, source, resource_name: "<ns>/<name>" }`) so a user can open ArgoCD, Grafana, Keycloak, Harbor, Gitea, Superset and similar services from a freshly recreated cluster. The next thing that user needs is the service's initial admin login, which today means running `kubectl get secret … -o jsonpath | base64 -d` by hand for every service on every recreate.

Measured on two local clusters (names only, values not read):

| Service | Secret (namespace varies) | Key(s) |
|---|---|---|
| Argo CD | `argocd-initial-admin-secret` | `password` (user `admin`) |
| Harbor | `harbor-secrets` / chart `<release>-core` | `HARBOR_ADMIN_PASSWORD` (user `admin`) |
| Gitea | `gitea-admin` | `admin-password` (+ username key or chart value) |
| Superset | `superset-credential` | `admin-password` (user `admin`) |
| Grafana (chart) | `<release>-grafana` | `admin-user`, `admin-password` |

Secret names and keys are deployment-specific, so detection must be a curated registry with fallbacks, not a guess.

This is a security-relevant change: AGENTS.md forbids exposing private-key contents to the frontend and logging secrets, and treats widening Tauri commands and filesystem/process access as design changes. A password shown in the UI is a deliberate, narrow exception that this ADR defines. It also stays inside the product boundary: ClusterDeck still does not list, edit or create accounts; it only reads an existing well-known login for an endpoint it already discovered.

## Decision

**D1 — Permission: the user's own credentials, checked twice.** Every call uses the profile's ClusterDeck-owned kubeconfig with `--kubeconfig <path> --context <ctx>` pinned for the whole operation (no ambient `KUBECONFIG`; the only fallback is the transport-level curl retry amended below). The kubeconfig is read once per action; those exact bytes are checked and copied to an exclusively created, owner-only (0600) temporary file under the ClusterDeck directory, shared by all kubectl calls and removed on exit. A kubeconfig whose selected user sets `as`, `as-groups` or `as-user-extra` (impersonation) is refused. `kubectl auth can-i get secret/<name> -n <ns>` runs first and only enables the action in the UI; the authoritative check is the GET itself, so a permission change between the two still fails closed. ClusterDeck never escalates or uses another credential: if the user could not run `kubectl get secret` themselves, ClusterDeck will not show it. (kubeconfig `exec` credential plugins run exactly as they already do for discovery; this ADR adds no new plugin trust.)

**D2 — Curated registry bound to the backend Service, one secret per endpoint.** Discovery records each endpoint's backend Service (`<ns>/<service>`) next to `resource_name`. A static Rust table maps a *known backend Service name* (e.g. `argocd-server`, `<release>-grafana`, `harbor-core`, `gitea-http`, `superset`) to exactly one `(secret name, username key | fixed username, password key)` in the backend Service's namespace. Hostnames, Ingress names and annotations are never used to choose a secret, so a look-alike Ingress cannot borrow another service's password; the UI also labels the login with the Service name, not the hostname. The candidate is resolved before any API call, so each click performs at most one `can-i` and one Secret GET, plus bounded backend validation reads. Unknown services show no login action. Each registry entry is unit-tested.

**D2 amendment (2026-11-16).** APISIX upstream Domain nodes must identify one distinct Service using exactly `<service>.<namespace>.svc` or `<service>.<namespace>.svc.cluster.local`, with DNS-1123 labels. Cache `<route namespace>/<upstream name>` alongside that backend; the Secret belongs to the target Service's namespace. Both permission check and reveal re-read that upstream and require the same exact-form target, then GET the Service and reject missing (`not_found`) or ExternalName (`backend_mismatch`) targets. Changed or unresolved bindings return `backend_mismatch`; legacy cross-namespace caches without provenance require a rescan. All reads are bounded and share the pinned kubeconfig snapshot/context. Ingress and APISIX `serviceName` remain namespace-local and need only the live Service check. Measured alias `harbor` shares the existing convention.

**D2 amendment — workload-derived Secret; Keycloak removed (2026-11-16).** Measured on a real cluster, the static Secret names were wrong or misleading: Grafana's chart used `admin.existingSecret` (`grafana-secrets`, not `<release>-grafana`), Gitea's `gitea-admin` carries no username key, and Keycloak's `keycloak-initial-admin` is the temporary bootstrap admin, commonly deleted after setup, so revealing it showed a login that returns 401. Keycloak is therefore removed from the registry. For entries with `workload_env` (Grafana `GF_SECURITY_ADMIN_USER`/`GF_SECURITY_ADMIN_PASSWORD`, Gitea `GITEA_ADMIN_USERNAME`/`GITEA_ADMIN_PASSWORD`), check and reveal first read the live backend Service's `spec.selector` (already fetched by the backend check), list at most 3 matching pods in the Service namespace (one raw `/api/v1/namespaces/<ns>/pods?labelSelector=<encoded>&limit=3` URL used by both `kubectl get --raw` and curl, selector keys/values validated and URL-encoded, 2 MiB bound, same kubectl-then-curl transport). Only qualified pods count: phase `Running`, `Ready=True`, no `deletionTimestamp`, and a controller ownerReference of kind ReplicaSet/StatefulSet/DaemonSet, so a stray, unready or terminating pod cannot vouch for a Secret; if qualified pods resolve to different logins (rollout, stray pod) workload resolution is not used and the static Secret applies. Within a pod, one container supplies both env vars (the container holding the password `secretKeyRef`, else the first container with a usable env; containers, then initContainers), so a sidecar's username is never combined with the app's password. The password must be `valueFrom.secretKeyRef` (a literal `value` is never accepted for a password); its Secret name (DNS label) and key (`[-._a-zA-Z0-9]`) are validated, and `can-i` plus the single Secret GET then target that Secret. The username is a literal `value` (not secret, still returned only on reveal; measured for Gitea, whose password env is also literal and therefore ignored, so the static Secret supplies the password) or a `secretKeyRef` key inside the Secret that will be read (including the static one when the password env is a literal). Any failure (pods forbidden, none found, oversized, unsafe name/key, no matching env) silently falls back to the static registry Secret; nothing from the pod spec is echoed and errors stay fixed codes. Check and reveal resolve independently, so the backend stays authoritative: the reveal response carries the Secret name it actually read and the reveal panel is labeled from that response, never from the earlier check result and never from frontend input. Cost: one extra bounded read per action (and Secret names containing dots fall back to static); escape hatch: remove the `workload_env` fields and `service_login/workload.rs`, restoring the static behavior.

**D2/D5 amendment — Keycloak returns as realm users + permanent admin; SSO accounts (2026-11-17).** The 0.8.1 removal was right about the *bootstrap* admin but left users of SSO-protected apps (a portal, a manager UI whose login is Keycloak OIDC) with no login at all: their real accounts are Keycloak realm users. Measured on two clusters: realm user passwords live in Secret `keycloak-user-passwords` in the Keycloak Service's namespace, one data key per username; the permanent admin is `keycloak-admin` or `keycloak-admin-credential` (keys `username`/`password`). Decision: (1) Backend Services `keycloak` and `keycloak-service` return to the registry as kind keycloak; reveal reads, each gated by its own `can-i get secret/<name>` and an authoritative GET, the first existing permanent admin Secret (label "Admin console (master realm)"; `keycloak-initial-admin` is never read) and `keycloak-user-passwords` (one account per data key matching `[A-Za-z0-9._@-]{1,64}`, others skipped, capped at 20). (2) Any other endpoint gets the realm users as an extra group "SSO (Keycloak realm <realm or unknown>)" only on evidence: the route's APISIX `openid-connect` plugin (recorded during discovery from the route JSON, field `sso_oidc`) or a literal env whose name contains `ISSUER` and whose value is `https://<host>/realms/<realm>` on a qualified backend pod (same pod rules as the workload amendment; `valueFrom` Secrets/ConfigMaps are never resolved, so an issuer kept in a Secret yields no evidence and no SSO group). The Keycloak Service is located only among the same profile's stored endpoints (issuer host match, else the single distinct Keycloak backend; ambiguity yields no group) and its backend is live-validated like any other (D2) before its namespace is used. (3) The reveal returns groups of accounts (the app's own admin and the SSO realm users are separate groups); each group has its own fixed error code, so one forbidden or missing source never hides another, and the call fails only when no group yields an account. The check enables the button when at least one source passes `can-i`. (4) Listing options may probe, per distinct unknown backend (capped at 20 per load), the Service and one bounded pod list to find an issuer env, so an app without any registry entry can still offer the SSO login. Cost: convention-based Secret names; up to three Secret GETs per click (Keycloak: admin candidates + users) and one extra pod read per check/reveal and per probed endpoint; Debug stays redacted for every account. Escape hatch: delete `service_login/keycloak.rs` and the `Source::KeycloakAdmin`/`RealmUsers` plan entries (and `sso_oidc`); the registry and single-account behaviour are untouched. Still no listing of arbitrary secrets, no writes: D5 widens only from "one secret per click" to "at most the endpoint's own admin Secret plus the Keycloak admin and realm-user Secrets".

**D2/D5 amendment 2 — more SSO evidence, incl. one outbound HTTP probe (2026-11-17).** Real clusters showed apps whose SSO is invisible to the first two sources: a portal whose issuer lives in an envFrom Secret (it serves NextAuth `/api/auth/providers`) and a Grafana configured only through `GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET` with no admin Secret. Evidence list, in order, per endpoint: (1) APISIX `openid-connect` plugin, (2) literal `*ISSUER*` env `https://<host>/realms/<realm>`, (3) a qualified backend pod container env *name* containing `OAUTH` or `OIDC` (names only; values and referenced Secrets are never read), (4) an HTTP probe of the app's public login surface. Sources 3 and 4 attach realm users only when the profile's stored endpoints contain exactly one distinct Keycloak backend; with two or more, nothing attaches (no guess). The probe is a **new outbound, read-only request from the user's machine to the cluster's own endpoint**, at most two GETs per endpoint and only for endpoints with no other evidence: `GET https://<host>/api/auth/providers` (evidence when any provider has `type` `oidc` or an id containing `keycloak`) and `GET https://<host>/` read for `%{redirect_url}` matching `https://<h>/realms/<realm>/protocol/openid-connect/auth` (evidence plus realm). It runs `curl -q -s --fail --proto =https --max-time 5 --max-filesize 65536 --resolve <host>:443:<stored ip>` through `CommandRunner` (`run_bounded`, 6 s, 64 KiB), host and ip validated with `is_safe_host_domain`/`is_safe_ip_address`, TLS verification on (no `-k`; a TLS failure is no evidence), redirects never followed, no cookies or credentials sent, results held only for the call. Options probe at most 20 endpoints, 4 at a time; check and reveal re-derive the evidence themselves (never trusting the frontend), so a probe-only app costs up to two extra requests per check and per reveal. When an app's own admin Secret is missing but SSO evidence exists, the reveal returns the SSO group plus an admin group with `not_found` instead of failing. Cost: network requests to cluster apps (visible in their access logs), probe latency, evidence that is heuristic (a provider list can name an unrelated OIDC provider; the user still sees the group label and realm). Escape hatch: delete `service_login/sso_probe.rs` and its two call sites in `plan.rs`, or drop only the env-name test; the plugin and issuer sources and all single-account behaviour are unaffected. Hardening from review: probe hosts must contain a dot and not be made only of numeric (decimal/octal/hex, inet_aton-style) labels, since curl would turn `127.1` into an address and ignore `--resolve`; the probe passes `--noproxy '*'` so inherited proxy variables cannot bypass the pin; a literal issuer env may pick one of several Keycloaks by host, but several Keycloak backends on the same host, or on none, attach nothing (never cache-order dependent), and the weak sources still require exactly one; the options load runs backend lookups and probes 4 at a time under a 15 s overall deadline, after which unresolved backends add no SSO option (registry options are always returned). The SSO group deliberately carries no cross-namespace route warning: realm credentials are typed into the Keycloak login page, not the app, so the route-owner capture premise of the D2 cross-namespace amendment does not apply.

**D2/D5 amendment 3 — per-profile SSO username template (2026-11-17).** Measured: on an LDAP-federated realm the `keycloak-user-passwords` keys (`admin`) are not the login names (`beluga-admin`), so key-as-username returned 401. `Profile.sso_username_template` (default `{key}`, persisted in profiles.yaml, validated at the store boundary: exactly one `{key}`, other characters `[A-Za-z0-9._@-]`, at most 64) maps each key to the displayed username for realm-user accounts only (never the Keycloak admin console account or an app's own admin); the result is re-validated as a safe username and the account is dropped if it is not, and the UI shows the key in small text when it differs. Cost: one more profile field the user must know; escape hatch: leave it empty (identity mapping).

**D3 — Read on explicit action only; never persisted; fixed errors.** Nothing is fetched during Scan/Connect. The command takes `(profile_id, endpoint_id)` where `endpoint_id` refers to an endpoint the backend itself stored for that profile; the backend re-derives namespace, Service and secret from its own record and re-validates profile id, namespace and secret name with a new Kubernetes DNS-name validator in `validate.rs` before building a fixed argv. The value is decoded in Rust, returned once, and never written to `profiles.yaml`, `state.json`, `endpoints.json`, local-DNS files, evidence or logs. Every failure maps to a fixed code (`forbidden_caller`, `forbidden`, `not_found`, `backend_mismatch`, `unsupported_service`, `impersonation_refused`, `timeout`, `kubectl_failed`) and never carries `kubectl` stdout/stderr. The secret type is not `Debug`/`Display`-printable. Calls are bounded (`run_bounded`, 10 s, 64 KiB).

**D2 amendment — cross-namespace warning (2026-11-16).** Whoever owns the APISIX route namespace controls the gateway route (plugins could capture login POSTs), so the Secret's namespace is not the only trust boundary. The backend copies the route namespace, route resource and host from its own stored endpoint record (never frontend input) into the option/reveal result; when the route namespace differs from the Service namespace the UI shows an explicit warning naming the route namespace, route and host, and the Reveal tooltip says so. Only non-secret metadata is added; Debug redaction is unchanged. This warns, it does not block.

**D4 — UI handling.** Password masked by default with *Reveal* and *Copy*; username in clear. Each request carries a generation number and a response arriving after navigation, profile switch or a newer request is discarded. The value clears from component state when the card collapses, the user leaves the screen, or after 60 s. Copy writes to the clipboard only on click and, after 60 s, clears it only if it still holds that value; the UI notes that clipboard managers may keep a copy. No toast, banner or log line ever contains the value. The command is exposed only to the app's own main window.

**D5 — Scope.** Read-only, one secret per click, only for endpoints discovered for the selected profile, only namespaces of their resolved backend Services. No listing of secrets, no write/rotate, no bulk export.

**D1 amendment — curl retry on kubectl transport failure.** Measured in the bundled macOS app: Local Network Privacy blocks third-party binaries spawned by the app (Homebrew `kubectl`) from reaching LAN API servers, while Apple's `/usr/bin/curl` is exempt; discovery and verify already use curl for this reason. Only when `kubectl` fails at the transport level (spawn error, timeout, or non-success without an authoritative API answer such as `Forbidden`/`NotFound`/`can-i` `no`), the same call is retried once through system curl against the *same* pinned snapshot and the *same* selected context's cluster and user (the snapshot is reduced to that context in memory; TLS is verified against its CA, never `-k`). Reads are `GET` of the Service/ApisixUpstream/Secret; `can-i` becomes a `SelfSubjectAccessReview` `POST` (no secret in the body). Every curl call is bounded like kubectl (10 s, 64 KiB); temp cert/key files are 0600 and removed; a `kind: Status` body maps 403 to `forbidden` and 404 to `not_found`, anything else to the kubectl error code (fixed codes only, no output echoed). Impersonation is still refused before any call; users relying on `exec`/`auth-provider` plugins or lacking a certificate/token cannot be served by curl, so kubectl's own error code stands. Cost: a second request on transport failure and a curl-capable credential subset. Escape hatch: remove the curl path in `service_login/transport.rs` to return to kubectl-only.

**D1 amendment 2 — curl hardening (security review).** The shared curl helper (`k8s_endpoints.rs`) now: starts with `-q` so `~/.curlrc` cannot inject options; passes the bearer token through an owner-only (0600, exclusive) header file (`-H @file`) removed on every return path instead of argv, where `ps` shows it; resolves `curl` to `/usr/bin/curl` first (Homebrew curl is not Local-Network-Privacy exempt); fails closed when a kubeconfig CA, client certificate or key cannot be decoded or written instead of falling back to the system trust store or going anonymous; reads `tokenFile` in preference to `token` (client-go precedence, so curl and kubectl present the same identity); and pins the kubeconfig's `current-context` rather than `clusters[0]`/`users[0]`. kubectl `Unauthorized` is authoritative and never retried, like `Forbidden`/`NotFound`; the ApisixUpstream lookup retries via curl only on transport failure. Cost: a few more refusals on malformed kubeconfigs; escape hatch: none wanted for the security properties, the curl path as a whole stays removable per the first amendment.

**D4 amendment — clipboard clearing via change count.** WKWebView denies `navigator.clipboard.readText()` (measured: the value was still on the clipboard after 62 s), so "clear only if unchanged" cannot be decided in the webview. Rust exposes `clipboard_change_count` and `clear_clipboard_if_change_count(expected)` (main window only), implemented with `osascript` + AppleScriptObjC over `NSPasteboard.generalPasteboard`; the script is fixed text and the only variable is an `i64` formatted by Rust, and the secret never reaches Rust. The UI records the count right after `writeText` and clears after 60 s only if it still matches; if the count cannot be read the note says the clipboard will not auto-clear. Cost: an `osascript` spawn per call and a tiny window between write and count read; escape hatch: remove the two commands and the UI note falls back to "will not auto-clear".

## Accepted residual risks

- The curl path cannot present a client certificate and a bearer token together; when a kubeconfig user carries both, the token is omitted and the request fails (no credential exposure, kubectl's error stands).
- The clipboard change-count read and clear have millisecond race windows (between `writeText` and the count read, and between the check and the clear). Another writer landing inside a window could be cleared or leave the value un-cleared; accepted given the 60 s auto-clear is best-effort.

## Verification

- Unit: registry entries; impersonation refusal; forged `endpoint_id`; `can-i` no ⇒ no GET; GET forbidden after `can-i` yes ⇒ `forbidden`; every failure path returns only fixed codes (assert no stderr/stdout content leaks); late-response discard in the UI hook.
- Transport fallback (FakeRunner): kubectl `no route to host` reveals via pinned curl (CA, no `-k`, selected context only); curl Status 403/404/garbage map to fixed codes; authoritative kubectl `Forbidden` is never retried; SelfSubjectAccessReview allowed/denied; exec-plugin users keep kubectl's code and never reach curl; discovery's ApisixUpstream list falls back to curl.
- Real cluster: an admin kubeconfig reveals each registered service; a namespace-scoped ServiceAccount kubeconfig without `get secrets` gets `forbidden` and no value.

## Consequences

- Removes the manual `kubectl get secret | base64 -d` step after every recreate.
- New Tauri command (`reveal_endpoint_login(profile_id, endpoint)`) and new `kubectl` invocations, both through `CommandRunner` with argv built from validated namespace/name (`validate.rs`, Kubernetes DNS-label rules).
- Registry maintenance: a renamed chart secret silently shows no login until the registry is updated.
- The value transits the Tauri IPC boundary and the WebView's memory; mitigated by D3/D4, not eliminated.

**Escape hatch:** the command can be removed or gated behind a per-profile `allow_credential_reveal: false` without data migration because nothing is persisted.

## Alternatives considered

- *Show a copy-able `kubectl` command instead of the value* — zero secret transit, but keeps the manual step the feature exists to remove.
- *Match by hostname or Ingress name* — rejected: spoofable by anyone who can create an Ingress in the namespace (D2).
- *Gate on cluster-admin only* — simpler but wrong both ways: namespace admins are excluded, and cluster-admin is not required to read one secret. Per-secret `can-i` matches what the user can already do.
- *Read every known secret during Scan* — convenient, but fetches secrets nobody asked for and widens exposure; rejected by D3.
